## 1. Назначение

База данных обслуживает сервис краткосрочной аренды велосипедов.

Основные бизнес-процессы:

* регистрация клиентов;
* хранение велосипедов и их моделей;
* бронирование велосипеда;
* начало и завершение аренды;
* продление аренды;
* приём платежей;
* передача велосипеда в ремонт;
* фиксация истории статусов;
* аудит действий пользователей и системы.


## 2. Основные сущности

### `CLIENTS`

Таблица содержит данные о клиентах сервиса проката велосипедов.

#### Назначение

Используется для хранения основной информации о пользователях, которые могут бронировать велосипеды, оформлять аренду и совершать платежи.

#### Основные данные

* ФИО клиента;
* номер телефона;
* адрес электронной почты;
* дата регистрации;
* текущий статус.

#### Статусы клиента

| Статус     | Описание                                     |
| ---------- | -------------------------------------------- |
| `ACTIVE`   | Клиент активен и может пользоваться сервисом |
| `BLOCKED`  | Клиент временно заблокирован                 |
| `ARCHIVED` | Клиент переведён в архив                     |

Физическое удаление клиентов не предполагается. Вместо удаления используется изменение статуса, что позволяет сохранять историю бронирований, аренд и платежей.

---

### `STAFF`

Таблица содержит сведения о сотрудниках и администраторах сервиса.

#### Назначение

Используется для:

* открытия и закрытия заявок на ремонт;
* выполнения административных операций;
* фиксации ответственного сотрудника;
* ведения истории изменений состояния велосипедов.

Пароли, хэши паролей и другие чувствительные данные авторизации в таблице не хранятся. Аутентификация должна быть реализована отдельно.

---

### `RENTAL_STATIONS`

Таблица содержит информацию о пунктах выдачи и возврата велосипедов.

#### Основные данные

* название станции;
* адрес;
* контактный телефон;
* текущий статус работы.

#### Статусы станции

| Статус               | Описание                          |
| -------------------- | --------------------------------- |
| `ACTIVE`             | Станция работает в обычном режиме |
| `TEMPORARILY_CLOSED` | Станция временно недоступна       |
| `CLOSED`             | Станция закрыта                   |

Станция может использоваться как текущее местоположение велосипеда, а также как пункт начала или завершения аренды.

---

### `BICYCLE_MODELS`

Справочник моделей велосипедов.

Таблица хранит характеристики, общие для всех физических велосипедов одной модели.

#### Основные данные

* производитель;
* название модели;
* тип велосипеда;
* стандартный почасовой тариф;
* описание.

Одна запись в `BICYCLE_MODELS` может соответствовать нескольким физическим велосипедам из таблицы `BICYCLES`.

---

### `BICYCLES`

Реестр физических велосипедов сервиса.

Каждая строка представляет отдельный инвентарный объект.

#### Основные данные

* уникальный инвентарный номер;
* модель велосипеда;
* текущая станция;
* текущий статус;
* индивидуальный почасовой тариф;
* дата покупки;
* дата последнего технического обслуживания.

#### Статусы велосипеда

| Статус      | Описание                                     |
| ----------- | -------------------------------------------- |
| `AVAILABLE` | Велосипед доступен для бронирования и аренды |
| `RESERVED`  | Велосипед зарезервирован                     |
| `RENTED`    | Велосипед находится в аренде                 |
| `REPAIR`    | Велосипед находится на ремонте               |
| `BLOCKED`   | Использование велосипеда временно запрещено  |
| `RETIRED`   | Велосипед выведен из эксплуатации            |

Если для велосипеда задан индивидуальный тариф, он имеет приоритет над стандартным тарифом модели.

---

## 3. Бронирование и аренда

### `BOOKINGS`

Таблица содержит предварительные бронирования велосипедов.

Бронирование хранится отдельно от фактической аренды, поскольку оно может:

* быть отменено;
* истечь;
* не перейти в аренду;
* завершиться без фактической выдачи велосипеда.

#### Основные данные

* клиент;
* велосипед;
* плановое время начала;
* плановое время окончания;
* срок удержания бронирования;
* статус;
* предварительно рассчитанная стоимость.

#### Статусы бронирования

| Статус      | Описание                            |
| ----------- | ----------------------------------- |
| `NEW`       | Бронирование создано                |
| `CONFIRMED` | Бронирование подтверждено           |
| `CANCELLED` | Бронирование отменено               |
| `EXPIRED`   | Срок действия бронирования истёк    |
| `COMPLETED` | Бронирование завершено и обработано |

Проверка пересечения активных бронирований для одного велосипеда должна выполняться в PL/SQL-пакете или специализированной процедуре.

Ограничения уровня таблицы недостаточно для проверки пересекающихся временных интервалов.

---

### `RENTALS`

Таблица содержит фактически начатые аренды.

Аренда может быть создана:

* на основании подтверждённого бронирования;
* без предварительного бронирования.

#### Основные данные

* клиент;
* велосипед;
* станция выдачи;
* станция возврата;
* фактическое время начала;
* плановое время окончания;
* фактическое время окончания;
* базовая стоимость;
* стоимость продлений;
* сумма штрафов;
* итоговая стоимость.

#### Статусы аренды

| Статус      | Описание                          |
| ----------- | --------------------------------- |
| `ACTIVE`    | Аренда активна                    |
| `OVERDUE`   | Плановое время возврата превышено |
| `COMPLETED` | Аренда завершена                  |
| `CANCELLED` | Аренда отменена                   |

Связь с `BOOKINGS` является необязательной, поскольку аренда может быть оформлена напрямую.

---

### `RENTAL_EXTENSIONS`

Таблица хранит историю продлений аренды.

Каждое продление записывается отдельной строкой.

#### Основные данные

* аренда;
* прежнее время окончания;
* новое время окончания;
* стоимость продления;
* статус операции;
* дата создания.

#### Статусы продления

| Статус      | Описание           |
| ----------- | ------------------ |
| `CREATED`   | Продление создано  |
| `PAID`      | Продление оплачено |
| `CANCELLED` | Продление отменено |

Хранение продлений отдельными записями позволяет сохранить полную историю изменений аренды и связанных начислений.

---

## 4. Платежи

### `PAYMENTS`

Таблица содержит платежи по бронированиям, арендам, продлениям и штрафам.

#### Типы платежей

| Тип         | Описание                 |
| ----------- | ------------------------ |
| `BOOKING`   | Оплата бронирования      |
| `RENTAL`    | Оплата аренды            |
| `EXTENSION` | Оплата продления         |
| `PENALTY`   | Оплата штрафа            |
| `REFUND`    | Возврат денежных средств |

#### Статусы платежей

| Статус     | Описание                  |
| ---------- | ------------------------- |
| `CREATED`  | Платёж создан             |
| `PENDING`  | Платёж обрабатывается     |
| `SUCCESS`  | Платёж успешно выполнен   |
| `FAILED`   | Платёж завершился ошибкой |
| `REFUNDED` | Средства возвращены       |

#### Основные данные

* сумма;
* валюта;
* способ оплаты;
* внешний идентификатор платежа;
* ключ идемпотентности;
* дата создания;
* дата успешной оплаты;
* дата ошибки;
* причина ошибки.

Поле `idempotency_key` используется для защиты от повторного списания при повторной отправке одного и того же запроса.

Одинаковый ключ идемпотентности не должен обрабатываться более одного раза.

---

## 5. Ремонт и техническое обслуживание

### `REPAIR_ORDERS`

Таблица содержит заявки на ремонт и техническое обслуживание велосипедов.

#### Основные данные

* велосипед;
* сотрудник, открывший заявку;
* сотрудник, закрывший заявку;
* описание проблемы;
* результат ремонта;
* стоимость работ;
* дата открытия;
* дата начала ремонта;
* дата завершения.

#### Статусы заявки

| Статус        | Описание           |
| ------------- | ------------------ |
| `OPEN`        | Заявка создана     |
| `IN_PROGRESS` | Выполняется ремонт |
| `COMPLETED`   | Ремонт завершён    |
| `CANCELLED`   | Заявка отменена    |

Велосипед не переносится в отдельную таблицу ремонта. Он продолжает храниться в `BICYCLES`, а его статус изменяется на `REPAIR`.

После завершения ремонта статус велосипеда может быть изменён на `AVAILABLE`, `BLOCKED` или `RETIRED` в зависимости от результата работ.

---

### `BICYCLE_STATUS_HISTORY`

Таблица содержит бизнес-историю изменения статусов велосипедов.

#### Назначение

Используется для:

* бизнес-аналитики;
* расследования инцидентов;
* восстановления последовательности событий;
* контроля действий сотрудников;
* отслеживания жизненного цикла велосипеда.

#### Основные данные

* предыдущий статус;
* новый статус;
* причина изменения;
* ответственный сотрудник;
* дата изменения;
* источник изменения;
* идентификатор связанного объекта.

В качестве источника изменения могут использоваться:

* бронирование;
* аренда;
* ремонт;
* ручная операция;
* системное действие.

Пример: при начале аренды статус велосипеда изменяется с `RESERVED` или `AVAILABLE` на `RENTED`, а источником изменения указывается аренда.

---

## 6. Аудит

### `AUDIT_LOG`

Общий технический журнал действий и изменений в системе.

#### Назначение

Таблица используется для фиксации значимых операций, выполняемых пользователями, сотрудниками, системными компонентами и непосредственно базой данных.

#### Основные данные

* тип инициатора;
* идентификатор инициатора;
* код действия;
* название сущности;
* идентификатор изменённой записи;
* старые данные;
* новые данные;
* идентификатор запроса;
* пользователь базы данных;
* IP-адрес;
* код ошибки;
* текст ошибки;
* дата и время события.

#### Типы инициаторов

| Тип        | Описание                                             |
| ---------- | ---------------------------------------------------- |
| `CLIENT`   | Действие выполнено клиентом                          |
| `STAFF`    | Действие выполнено сотрудником                       |
| `SYSTEM`   | Действие выполнено приложением или фоновым процессом |
| `DATABASE` | Действие выполнено триггером или PL/SQL-кодом        |

#### Примеры событий

* `BOOKING_CREATED`;
* `BOOKING_CONFIRMED`;
* `RENTAL_STARTED`;
* `RENTAL_EXTENDED`;
* `PAYMENT_FAILED`;
* `REPAIR_OPENED`.

Поля `old_data` и `new_data` хранятся в формате JSON.

Журнал аудита должен работать по принципу append-only:

* разрешено добавление новых записей;
* изменение существующих записей запрещено;
* удаление записей запрещено для обычных пользователей;
* доступ к журналу должен быть ограничен административными ролями.

---

## 7. Основные связи

Ниже представлена логическая структура связей между сущностями.

```text
CLIENTS
├── BOOKINGS
├── RENTALS
└── PAYMENTS

RENTAL_STATIONS
├── BICYCLES
└── RENTALS

BICYCLE_MODELS
└── BICYCLES

BICYCLES
├── BOOKINGS
├── RENTALS
├── REPAIR_ORDERS
└── BICYCLE_STATUS_HISTORY

BOOKINGS
├── RENTALS
└── PAYMENTS

RENTALS
├── RENTAL_EXTENSIONS
└── PAYMENTS

STAFF
├── REPAIR_ORDERS
└── BICYCLE_STATUS_HISTORY
```

### Ключевые отношения

| Родительская сущность | Дочерняя сущность        | Тип связи              |
| --------------------- | ------------------------ | ---------------------- |
| `CLIENTS`             | `BOOKINGS`               | Один ко многим         |
| `CLIENTS`             | `RENTALS`                | Один ко многим         |
| `CLIENTS`             | `PAYMENTS`               | Один ко многим         |
| `RENTAL_STATIONS`     | `BICYCLES`               | Один ко многим         |
| `RENTAL_STATIONS`     | `RENTALS`                | Один ко многим         |
| `BICYCLE_MODELS`      | `BICYCLES`               | Один ко многим         |
| `BICYCLES`            | `BOOKINGS`               | Один ко многим         |
| `BICYCLES`            | `RENTALS`                | Один ко многим         |
| `BICYCLES`            | `REPAIR_ORDERS`          | Один ко многим         |
| `BICYCLES`            | `BICYCLE_STATUS_HISTORY` | Один ко многим         |
| `BOOKINGS`            | `RENTALS`                | Ноль или один к одному |
| `BOOKINGS`            | `PAYMENTS`               | Один ко многим         |
| `RENTALS`             | `RENTAL_EXTENSIONS`      | Один ко многим         |
| `RENTALS`             | `PAYMENTS`               | Один ко многим         |
| `STAFF`               | `REPAIR_ORDERS`          | Один ко многим         |
| `STAFF`               | `BICYCLE_STATUS_HISTORY` | Один ко многим         |

Связь между `BOOKINGS` и `RENTALS` является необязательной: бронирование может не перейти в аренду, а аренда может быть создана без бронирования.
